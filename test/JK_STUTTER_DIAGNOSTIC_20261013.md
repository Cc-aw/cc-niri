## 归因与限制

1. **已证实：有窗口工作区切换会真实漏帧，严重时画面约 100ms 没有新呈现。** 相当于 60Hz 下缺少约 5 个中间更新。项目并非仅有启动失败或快捷键无响应。
2. **较强证据：问题位于 KWin 主线程上的切换 / 场景 / 效果工作路径。** 空工作区对照明显较轻，有窗口组在去掉每轮探针后仍复现。两组包含不同应用窗口，且采样方式不完全相同，不能仅凭列数确定哪个应用或效果负责。
3. 第一轮与对照并非同窗口负载的严格 A/B。中途曾推测临时脚本加载放大了长停顿；随后无每轮探针的有窗口组再次复现，**不能将长停顿主要归因于探针，也不能声称探针完全无影响**。
4. 原生 WorkspaceSlideAdapter 对目标输出窗口保持可绘制引用并启用 ForceBlur / ForceBackgroundContrast（`native/viewport-clip/WorkspaceSlideAdapter.cpp:77`），在每个输出 paint pass 使用 compositor 预测呈现时间。JS workspace mount 同步执行挂载、布局与发布（`src/kwin/workspace/WorkspaceSwitchController.js:98`）。这些是后续 CPU 调用栈检查的候选路径，尚未证明其中某一处耗时。
5. Focus Ring refresh 在 fullscreen effect 活跃时清理 Ring（`native/focus-ring/FocusRingEffect.cpp:155`），Native workspace animation 使用 fullscreen ownership，因此没有依据直接认定 Ring 栅格化是切换中段的原因。
6. CLEAR 日志来自清理窗口 marker，不能仅凭次数认定是每帧清理或循环故障。未以日志数量当成调用栈归因。
7. 无可用 `perf` 调用栈采集工具，未取得函数级热点；未卸载 Ring / Blur 做组件 A/B。GPU 低频样本在调度组结束附近及之后取得，不能对掉帧瞬间 GPU 负载归因。沙箱内 nvidia-smi 的设备访问失败不代表驱动故障，沙箱外只读采样成功。
8. 本次切换的是多列 / 空工作区，未建立启用单列居中前后的同负载基线，不能断言新功能引入了卡顿，也不能证明其绝对无影响。

后续修复应先取得有窗口工作区切换期间的 CPU 调用栈，区分 JS mount / Qt 场景处理 / Blur 与驱动提交；然后以相同窗口负载复测。单纯缩短 420ms 不会消除 67–100ms 的漏帧，不应作为掉帧修复。
